# Роли и права

Сервер является единственным источником решения о доступе. Frontend использует ту же матрицу только для навигации и UX; скрытая кнопка не является защитой.

## 1. Роли

- USER — каталог, создание и доступные пользователю заявки, собственный профиль.
- OPERATOR — обработка назначенных лично и групповых заявок.
- CATALOG_ADMIN — каталог, папки, услуги, публикация и доступность.
- FORM_ADMIN — формы, версии, черновики и публикация.
- SLA_ADMIN — правила SLA, порядок, тестирование и предупреждения конфликтов.
- SYSTEM_ADMIN — все системные права и все административные страницы.

Права ролей суммируются. SYSTEM_ADMIN включает все права. Наличие accessKey не дает ни одной роли.

Frontend-реализация этапа 4 находится в js/core/permissions.js. Она используется только для route guard и скрытия навигации. После загрузки защищённой страницы актуальный пользователь и роли запрашиваются через authGetCurrentUser; локальный снимок не является серверным доказательством права.

## 3. Доступ к страницам

| Страница | Условие |
|---|---|
| login.html | анонимный или авторизованный |
| service-catalog.html | активная сессия |
| service-form.html | активная сессия + доступ к serviceId |
| requests.html | USER, OPERATOR или SYSTEM_ADMIN; набор строк фильтрует сервер |
| request-card.html | USER, OPERATOR или SYSTEM_ADMIN + доступ к entityId |
| profile.html без id | активная сессия, собственный профиль; self-update только language/timezone |
| profile.html?id=... | SYSTEM_ADMIN либо id текущего пользователя |
| admin/catalog-editor.html | CATALOG_ADMIN или SYSTEM_ADMIN |
| admin/forms.html | FORM_ADMIN или SYSTEM_ADMIN |
| admin/form-editor.html | FORM_ADMIN или SYSTEM_ADMIN |
| admin/sla-editor.html | SLA_ADMIN или SYSTEM_ADMIN |

При отсутствии роли показывается forbidden без загрузки административных данных. Любая функция сервера повторяет проверку.

Текущие guards:

- catalog-editor: CATALOG_ADMIN или SYSTEM_ADMIN;
- forms/form-editor: FORM_ADMIN или SYSTEM_ADMIN;
- sla-editor: SLA_ADMIN или SYSTEM_ADMIN;
- requests: USER, OPERATOR или SYSTEM_ADMIN; список дополнительно ограничивается серверным объектным scope;
- request-card: USER, OPERATOR или SYSTEM_ADMIN; чтение, обработка и INTERNAL дополнительно проверяются по объекту;
- остальные пользовательские страницы: активная сессия и объектная проверка соответствующей вертикали.

## 4. Объектные правила

### Услуга

Пользователь видит и использует только PUBLISHED. При ALL достаточно активной сессии. При RESTRICTED требуется совпадение userId, departmentId либо хотя бы одной organizationId. Администраторский просмотр черновиков регулируется соответствующей admin-ролью.

### Заявка

- USER: автор, заявитель либо иной доступ, явно заданный серверной политикой.
- OPERATOR: персональный assignee, член responsibleGroup либо иной доступ серверной политики.
- SYSTEM_ADMIN: любая заявка.
- Публичный комментарий требует права чтения заявки.
- Внутренний комментарий требует OPERATOR/SYSTEM_ADMIN и права обработки заявки.
- Изменение статуса/назначения требует OPERATOR/SYSTEM_ADMIN и права обработки.
- Вложения требуют права чтения; upload/delete дополнительно права изменения.

### Профиль

Обычный пользователь читает свой профиль и меняет только `language` и `timezone`. SYSTEM_ADMIN может открыть и редактировать чужой профиль: основные данные, active, роли, организации, подразделение и группы. `id` и `login` не меняются этим контрактом. Роли, организации, подразделение и группы никогда не принимаются от обычного пользователя.

### Формы и SLA

FORM_ADMIN меняет только Form/FormVersion, SLA_ADMIN — только SlaRule. Ссылка услуги на опубликованную версию управляется CATALOG_ADMIN, но сервер проверяет существование и статус версии. Изменение порядка SLA — единая конкурентная операция.

## 5. Серверная проверка

Каждая защищенная функция выполняет в порядке:

1. Проверка sessionToken, expiresAt и revokedAt.
2. Загрузка актуального пользователя и ролей из доверенного источника.
3. Проверка action permission.
4. Загрузка объекта в пределах разрешенного scope.
5. Проверка object permission.
6. Проверка бизнес-инвариантов и expectedVersion.
7. Изменение и аудит.

Запрещено доверять переданным userId, organizationIds, groupIds, roles, authorId и createdBy. Автор и инициатор берутся из сессии. requestedFor проверяется отдельно.

## 7. Аудит отказов

Сервер журналирует requestId, actorId (если определен), action, entityType/id и итог allow/deny. Токены, пароль, accessKey и чувствительные значения полей не журналируются. Клиенту возвращается FORBIDDEN без раскрытия существования недоступного объекта; для чувствительных ресурсов допустимо унифицировать NOT_FOUND и FORBIDDEN.
